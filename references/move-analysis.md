# Move analysis guidance

## Functional coding

A rhetorical move is a communicative function, not a keyword or subject. The sentence “We use panel data” can preview design in an Introduction, construct a sample in Method, or orient a robustness test in Results. Code it from context.

## Induction process

1. Read complete pilot modules.
2. Write a one-line functional gloss for every paragraph.
3. Merge glosses that perform the same reader-facing job.
4. Split codes that share a topic but do different jobs.
5. Test whether another coder/model could distinguish the codes using inclusion/exclusion cues.
6. Recode the pilot with the candidate codebook.
7. Freeze definitions before coding remaining development papers.

Prefer a small, discriminating inventory. Very large codebooks produce low agreement and weak style rules.

## Primary and secondary moves

Choose the primary move by asking what would be lost if the paragraph were removed. Add secondary moves only when they are substantively developed, not merely mentioned.

## Coding QA

Review:

- every low-confidence paragraph;
- paragraphs with three or more moves;
- first/last paragraphs of each module;
- hypothesis/proposition paragraphs;
- table/figure-adjacent paragraphs;
- samples from every article and method group.

If coding is automated, report it as a first pass. Do not imply human intercoder reliability unless it was actually measured.

## Stability metrics

Use article coverage to decide whether a move is structurally stable. Use paragraph frequency only to understand repetition/intensity. Use normalized first position and adjacent transitions to understand sequence.

When a paragraph has multiple moves, sequence analysis should normally use the primary move. Report this choice.

## Interpreting method differences

A method difference can arise because of design requirements rather than journal style. Examples:

- experiments require manipulation and validity reporting;
- qualitative work requires access, positionality, and coding procedures;
- quasi-experiments require counterfactual and identifying assumptions;
- simulations require model calibration and sensitivity analysis;
- clinical studies may require preregistration, outcomes, and safety reporting.

Represent these as variants within a journal guide, not contradictory universal rules.

## From statistics to recommendations

Keep two layers:

1. **Observation:** “Move X appears in 10/12 development papers.”
2. **Recommendation:** “Use X as a default because it answers the reader's need for ...”

The recommendation needs a communicative rationale. High frequency alone does not make a practice good; low frequency can reflect optional formats or extraction/coding limits.

## Holdout discipline

Before viewing holdout, freeze:

- extraction rules;
- codebook;
- thresholds;
- development style guide;
- evaluation questions.

During validation, code holdout with the frozen definitions. Record mismatches. Do not create a new move from holdout unless the validation phase is complete and the revision is explicitly versioned as post-holdout.
